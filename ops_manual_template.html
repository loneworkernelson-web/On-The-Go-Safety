Part 1: Security Keys — The Golden Rule

🔐 Save Your Keys — Right Now

Your system uses two secret keys generated in Factory Step 1. These must be saved somewhere secure (e.g. a password manager) before you proceed with deployment.

KeyPurposeWho Needs It
Secret Key (Admin)Authenticates the backend script. Used to access the spreadsheet and unlock the Monitor.Administrators only — never share.
Worker Key (App)Authenticates worker devices connecting to the backend.Embedded in config.json — workers don't enter it manually.

⚠️ If you deploy with different keys later: Every device will lose its connection and require a full reinstall. If you use the same keys in future config updates, devices update seamlessly in the background. There is no penalty for keeping the same keys indefinitely.

Where to find your keys: Open the OTG Factory app (index.html) — your keys are shown in Step 1 → Security Connection Keys. The Factory remembers them between sessions using your browser's local storage. They are not re-printed in this document for security reasons.

Install the Backend (Factory Step 3)

The backend is a Google Apps Script that handles all safety logic — overdue detection, email alerts, SMS, AI report processing, and data archiving.

A. Paste the Code

  1. In the Factory, click "📋 Copy System Code".
  2. In your Google Sheet, go to Extensions → Apps Script.
  3. Delete all existing code in the editor.
  4. Paste and click Save (disk icon).

B. Grant OAuth Permissions (appsscript.json)

Google Apps Script does not automatically grant mail-sending scope. You must explicitly declare the required OAuth scopes by pasting the generated appsscript.json into your project settings.

  1. In the Factory, click "📋 Copy appsscript.json" (Step 3 — Grant Permissions block).
  2. In the Apps Script editor, click the ⚙ Project Settings gear icon (left sidebar).
  3. Scroll to "Show 'appsscript.json' manifest file in editor" and tick the checkbox.
  4. Return to the Editor tab — you will now see appsscript.json in the file list.
  5. Click it, select all, and replace the entire contents with what you copied from the Factory.
  6. Click Save.
  7. Deploy or re-deploy the Web App. When prompted for authorisation, click Review Permissions → choose your Google account → Allow.
What this unlocks: The Factory-generated appsscript.json declares all required scopes: Sheets, Drive, MailApp, Gmail (send, and full mailbox access for the Privacy Shredder), external requests, script management, and user identity. Without the mail scopes, MailApp.sendEmail will fail with a permissions error even though your script appears to run normally.
Use a dedicated Google account. The Privacy Shredder (cleanupPrivateSentNotes) searches the account's Sent mail and moves private note emails to the trash. Google only allows that with the full Gmail scope https://mail.google.com/, and its consent screen words it as "read, compose, send and permanently delete all your email". The script only touches threads whose subject is [PRIVATE] Note to Self, but the permission itself is broad. Run the system on a Google account that is used for nothing else, so the permission can only ever reach system mail. Do not install it on a personal or day-to-day work account.
Existing installation? Add the scope by hand. Installations set up before this scope was added will show "Private note sweep" as failing in the daily Health email, with a permissions error in the Executions log. Fix: open appsscript.json, add "https://mail.google.com/" to the oauthScopes list (or paste the new manifest from the Factory), save, run cleanupPrivateSentNotes once from the editor and click Review Permissions → Allow. If the hourly trigger still fails afterwards, delete it and add it again.
Re-authorisation required after scope changes: Any time you paste a new version of Code.gs or appsscript.json that adds a scope not previously granted, the script will throw a permissions error on the next run. The fix is the same — paste the new appsscript.json and re-authorise when prompted after deploying.

C. Deploy as a Web App

  1. Click Deploy (blue button) → New Deployment.
  2. Click the gear icon ⚙ next to "Select type" → choose Web App.
  3. Set Execute as: Me.
  4. Set Who has access: Anyone.
  5. Click Deploy. Accept the permissions prompt.
  6. Copy the Web App URL — you'll need it in Step 3 of the Factory.

D. Set Up Triggers (Automated Tasks)

Triggers are the automation engine — without them, overdue detection and alerting will not work. Set up all five:

A. Safety Watchdog Required
checkOverdueVisits
⏱ Time-driven · Every 1 minute

Scans for workers who haven't checked out or confirmed safety within the grace period. Fires email + SMS alerts. Must be 1 minute — a 10-minute interval causes Critical Timing (High-Risk mode) alarms to fire up to 10 minutes late.

B. Privacy Shredder Required
cleanupPrivateSentNotes
⏱ Time-driven · Every hour

Moves private "Note to Self" emails out of the Sent folder to the trash. Needs the full Gmail scope (see Step 3B).

C. Daily Health Report Recommended
sendHealthEmail
⏱ Day timer · e.g. 7am–8am

Emails a daily system summary — visit counts, escalations, failed alert emails, any stale open visits. Your early-warning system.

D. Data Archiver Optional
archiveOldData
⏱ Month timer · 1st of the month, 2am-3am

Once a month, moves completed visits older than 30 days to an Archive tab (and old form records into FormsArchive). Only closed visits are moved — active records are never touched.

E. Weekly Safety Summary Optional
sendWeeklySummary
⏱ Week timer · e.g. Monday 7am–8am

Emails a brief weekly digest — total visits, distance travelled, and safety alerts fired in the past 7 days. Useful for management reporting without opening the spreadsheet.

How to add triggers: In the Apps Script editor, click the Alarm Clock icon in the left sidebar → + Add Trigger (bottom right). Set the function name, source (Time-driven), and interval as shown above for each trigger.

Return to the Factory, go to Step 3, paste your Web App URL into the URL field, then click "📡 Test System Connection". A green "System Link Established" response confirms everything is working before you proceed.

Reading the Cards and the Status Panel

  • Times are shown the New Zealand way (for example 5:34 pm), and "minutes ago" is counted on the server's clock, so a supervisor's computer with the wrong time cannot make a visit look older or newer than it is.
  • Last Heard on each card is the last time the server heard anything from the worker's phone on that visit (it comes from Visits column AF). A phone that has been silent for a while is marked as stale on its card whatever its status, and counted in the header.
  • Finished visits (departed, completed, marked safe and similar) are never shown as red OVERDUE, even if the due time has passed.
  • Current Status per Visit (the panel that used to be called Activity Log) lists the latest status of each visit, one line per visit. It is not an event history, because the Visits tab keeps one row per visit. For the full history of what the system did, use the Audit tab (see Part 4).
  • Export downloads the same list as a CSV file named OTG_VisitStatus_<date>.csv with the columns Last update (UTC), Last update (local), Worker, Current status, Location and Last heard (local).

The Map

The map uses OpenStreetMap tiles by default. That needs no account and no key, and the map shows the required "© OpenStreetMap contributors" credit. OpenStreetMap's tile policy is written for light use (a few supervisors with the Monitor open), not for heavy or automated use.

CARTO now wants a key for its free map tiles. If you want the CARTO "Voyager" look, you can add a free CARTO key for your organisation:

  1. In Factory Step 1, find the CARTO map key field (next to the what3words field) and click Get Key (carto.com/basemaps/apikey). The key is free for non-commercial use including non-profits (up to 5 million map tiles a month).
  2. Leave any "website restriction" on the key blank, and do not share the key.
  3. Paste the key into the Factory field and download the Monitor again. A blank field means OpenStreetMap.
Automatic fallback: if CARTO refuses the key or the free allowance runs out (after four tile errors), the Monitor switches itself to OpenStreetMap and shows "Map: CARTO tiles unavailable - using OpenStreetMap". Treat the downloaded Monitor file like a password, because the key is inside it. Workers' phones do not use map tiles, so this only affects the Monitor.

A visit at a named site appears on the map at the site's recorded position (Sites column M, filled by the weekly geocoder), including visits recorded as "Company - Site".

Alarms, Acknowledging and Escalation Steps

  • Every status that makes the siren sound now also brings up the full-screen alarm: SOS, PANIC, OVERDUE ALARM, EMERGENCY, the standard overdue alerts (tiers 1 to 3) and a missed welfare check. Before this change the overdue steps and missed welfare checks sounded the siren without the full-screen alarm.
  • Acknowledging an alarm covers one step. When the escalation moves up to the next step, the full-screen alarm appears again and shows "Worker name - STATUS", so a supervisor who acknowledged the 15-minute alert still has to acknowledge the 30-minute one.
  • DURESS keeps its own quiet handling (see the Duress protocol above).

Resolving an Alarm from the Monitor

Use Resolve on an alarm card when a supervisor has confirmed the worker's situation by other means. The Resolve box asks for three things:

  1. The worker's name, typed exactly (a safeguard against resolving the wrong person).
  2. A resolution note (at least five characters). It is saved in the visit's Notes.
  3. Has the worker left? You must choose one:
    • Worker has left / visit is over - close the visit. The visit is closed.
    • Still on site - keep monitoring, due out in 10, 30 or 60 minutes. The visit goes back to active (ARRIVED, or TRAVELLING for a trip) and stays open. The due time becomes the later of the existing due time and now plus the minutes you chose, and a fresh escalation runs from that new due time. If the worker neither extends nor departs, the alarm runs again.
Good to know:
  • "Still on site" is greyed out when the alarm row has no readable due time, or when the backend is older than build __53_. Resolving then closes the visit.
  • The All Clear goes to whoever was alerted (nobody is told if no contact was ever alerted). When you chose "still on site", it says the worker is still being monitored. Its wording still says the worker "has confirmed they are safe", even when headquarters resolved the alarm.
  • The worker's phone is not told about the resolve. It may stay on its alarm screen until the worker enters their PIN.
  • Deploy backend __53_ before the new Monitor (__14_). The Monitor turns "still on site" off by itself if the backend reports an older build.

Re-Registering a Worker on a New Device

Each worker's app installation is bound to a specific device. When a worker first completes the setup wizard, the backend writes a unique device ID to column E of their row in the Staff tab. This prevents their account from being claimed by a different device without administrator approval.

If a worker gets a new phone, reinstalls the app, or needs to register from a different device, the existing binding must be cleared first. The worker will see the message "This worker is already registered on another device. Ask your administrator to clear the existing registration." if they attempt to register without this step being completed.

⚠️ Confirm Identity Before Clearing

Clearing column E allows any device to claim that worker's identity. Confirm directly with the worker — in person or by phone — that it is genuinely them requesting the re-registration, before proceeding.

To re-bind a worker to a new device:

  1. Open your Google Sheet and go to the Staff tab.
  2. Find the worker's row.
  3. Click the cell in column E (DeviceId) — it will contain a long alphanumeric string.
  4. Delete the cell contents and press Enter. Leave the cell empty — do not replace the value with anything.
  5. Tell the worker they can now open the app and complete the setup wizard again on their new device. The new device ID will be written to column E automatically on successful registration.
No redeploy needed. Clearing column E takes effect immediately — the backend checks the cell value live on each registration attempt. You do not need to redeploy the Apps Script or regenerate config.json.

The Settings Tab

Day-to-day behaviour that used to need a Factory rebuild is now controlled from a Settings tab in the Google Sheet. The backend creates the tab itself within a minute of the first run of the Safety Watchdog trigger and adds any missing key with its default. It never changes a value you have set. Phones pick up changes at their next sync; the backend reads the tab on its next run. If a key is deleted, it comes back with its default within the hour. If a value cannot be understood, the backend uses the default and names the key in the daily Health email.

On/Off keys accept On, Off, yes, no, 1, 0 or a ticked checkbox.

The Audit tab is a debugging trail, not a record. It keeps the last 7 days or 10,000 rows, whichever limit is reached first (the Settings keys above), and is trimmed each morning just before the Health email, as its own step, so a failed email still trims. The newest row always stays. Do not sort the Audit tab - the oldest rows must stay at the top. The permanent records are the Visits and Forms tabs. If your organisation needs a longer trail, copy the Audit rows out regularly or raise the two keys. The Health email's "Audit trail" row says how many rows were removed. If it removes rows younger than the days limit, the row limit is too low for your volume.

Phone Numbers

Phone numbers must stay as text with their leading zero (for example 0226003534) or in international form (+64226003534). If a spreadsheet turns a number into a plain number, the leading zero is lost and the number no longer dials correctly. The system writes numbers into the Visits tab as text, and when it builds an alert it restores the leading zero on an 8 to 10 digit number that has lost it. The Staff tab holds no phone numbers.

Part 5: Updates & Configuration Changes

Performing a Config-Only Update (Recommended)

Under the Config Model, most changes — branding, intervals, feature toggles — only require replacing config.json. The worker app detects the updated version field and refreshes automatically.

1

Open the Factory

Open index.html (the Factory app). Your previous settings should be remembered in the browser's local storage. If not, re-enter them — especially your keys.

⚠️ Use your original keys. If you click 🔄 to regenerate new keys, devices will lose connection. Only use the same keys you originally deployed with.
2

Adjust Settings

Change whatever needs updating — new branding colour, different grace period, toggle a feature on or off, new API key, etc.

3

Download & Deploy Updated Files

Go to Factory Step 4 and download the Worker App Pack ZIP. For a config-only update, you only need to replace config.json on your Netlify site — drag just that file onto your existing site's dashboard (not the Netlify Drop page). The version stamp in the file changes automatically, triggering devices to refresh their cached config at next connection.

If your branding has also changed, replace manifest.json and icon.png from the new pack at the same time.

When the worker app itself has changed (the Factory shows the build under the Step 4 buttons), replace index.html, sw.js and config.json together. config.json carries the worker build, so replacing it alone makes phones show a false "App out of date" banner.
4

Backend Changes (if any)

If you also changed backend settings (API keys, escalation logic), you need to re-copy the Code.gs and deploy a new version in Apps Script. See the "New Version Trap" warning below.

⚠️ The "New Version" Trap — Apps Script

When you edit code in Google Apps Script, clicking Save does not update the live system. For any change to take effect:

  1. Click Deploy (blue button).
  2. Select Manage Deployments.
  3. Click the Pencil icon (Edit).
  4. Change "Version" to "New version".
  5. Click Deploy.

⚠️ Re-Authorisation After Scope Changes

If you deploy updated backend code that adds new OAuth scopes (or paste a new appsscript.json), the script will throw a permissions error on its next run until re-authorised. To re-authorise:

  1. Open your Google Sheet → Extensions → Apps Script.
  2. Deploy → Manage Deployments → Edit → New version → Deploy.
  3. When prompted, click Review Permissions → choose your Google account → Allow.

You will only see the permissions prompt if a new scope has been added. If the prompt does not appear, the existing authorisation already covers all declared scopes.

Modifying the Backend Logic (Advanced)

You can edit Code.gs directly to change system behaviour — email formatting, AI prompts, alert thresholds, etc.

  • Go to your Google Sheet → Extensions → Apps Script
  • Find the function to change (e.g. smartScribe for AI, sendAlertEmail for notifications)
  • Test with the Run button before deploying
  • Always follow the "New Version" deployment steps after saving changes

Part 6: Advanced Features

ntfy Push Notifications

ntfy is a free, open-source push notification service that delivers instant alerts directly to contacts' phones the moment an alarm fires — no email delay, no polling required.

  • Admin setup: Enter your ntfy server URL in Factory Step 1 (leave blank to use the free hosted ntfy.sh service). For improved privacy and reliability, ask your IT Advisor to set up a self-hosted ntfy server — it runs on an inexpensive VPS and requires no changes to the OTG AppSuite itself. Simply paste your server URL here once it is ready.
  • Worker setup: Workers enter their contacts' ntfy topic names in the app setup wizard (or later via Settings). The app automatically stores these topics in columns H and I of the Staff sheet — the escalation engine reads them from there when sending overdue alerts, so no manual data entry is required from the administrator.
  • Contact setup: Contacts install the ntfy app and follow the setup steps in the Worker Guide (Section 13). The most important steps for reliability are enabling Instant Delivery (Android) and granting Time-Sensitive notification permissions (iOS). See the Worker Guide for full instructions. Contacts should also allow ntfy to override Do Not Disturb for urgent messages (every overdue alert is sent as urgent) and test it with the phone locked.
  • Verify with diagnostics: Use OTG Admin → Run System Diagnostics to confirm ntfy is reachable. Subscribe to the diagnostics topic (shown in the diagnostic email) to confirm end-to-end push delivery from your server to the ntfy app.
iOS limitation: The ntfy iOS app does not currently support Critical Alerts — the notification tier that overrides the physical mute switch. iPhone contacts should leave their mute switch off if they are on-call as an emergency contact.
Not receiving ntfy alerts during overdue escalations? This is a known issue with the free ntfy.sh service. Google's time-based trigger scripts run from a shared pool of IP addresses; if that pool has been rate-limited by ntfy.sh, push notifications sent during overdue checks will fail silently (the diagnostic and immediate-alarm paths use different IPs and are unaffected). Two solutions are available — choose one:
  • Proxy (recommended for existing cPanel hosting): Upload the included proxy_ntfy.php script to your shared hosting, then enter the proxy URL and secret in Factory Step 1 and redeploy the backend. The backend will route trigger-path ntfy calls through your hosting's clean IP. See the IT Advisor Overview (Section 6.5) for full setup steps.
  • Self-hosted ntfy: Run your own ntfy server on a VPS. Your server's IP is clean and not subject to shared-pool rate limiting. See IT Advisor Overview Section 6.4.
  • ntfy.sh paid plan: Authenticated requests to ntfy.sh bypass IP rate limiting. No proxy or self-hosting required.
Panic and Duress alarms, and Critical Timing overdue alarms, are not affected — they fire ntfy from the immediate-response path rather than the time-based trigger.

Already have a proxy? The proxy must forward five headers: Title, Priority, Tags, Click and Actions. Click and Actions carry the tap-to-call and map buttons on contacts' alerts (and, when WORKER_APP_URL is set, the tap action on worker reminders). An older proxy silently drops them: the alert still arrives, but without the buttons. Edit the one line in your live proxy_ntfy.php that reads foreach (['Title', 'Priority', 'Tags'] as $h) so it becomes foreach (['Title', 'Priority', 'Tags', 'Click', 'Actions'] as $h), or upload the new file from the Factory (Step 1, ntfy section). See ntfy_proxy_setup.md.

SMS Text Alerts

The system can send an SMS text message to emergency and escalation contacts the instant an alarm fires, in addition to email and ntfy push. SMS is a useful backup channel — particularly for contacts who haven't installed ntfy, or when email delivery is delayed. Credits are consumed per message sent.

The SMS provider is selected per-deployment in Factory Step 1 based on your region. The correct provider and credential fields are shown automatically when you select your country.

Healthchecks.io Dead-Man's Switch

The backend's escalation engine runs every ~15 minutes via a trigger. If that trigger silently stops firing (a known Google Apps Script limitation), workers could reach overdue status without any alarm. Healthchecks.io catches this.

  • Sign up free at healthchecks.io
  • Create one check with a 5-minute period and 3-minute grace
  • Copy the ping URL and paste it into the Healthchecks.io Ping URL field in Factory Step 1
  • The backend pings this URL after every successful escalation check. If it goes silent for ~8 minutes, Healthchecks.io emails you — well before any worker could reach overdue status
Strongly recommended for any organisation where worker safety is critical. The free tier supports up to 20 checks.

Daily Health Report Email

When the sendHealthEmail trigger is configured (Trigger C), the system emails a daily summary each morning containing:

  • Total visits logged in the past 24 hours
  • Number of escalations fired
  • Any alert emails that failed to send
  • Workers with an open visit older than 24 hours (stale records)

Configure the recipient in Factory Step 1 (System Health Report Email). If left blank, the report goes to the Google account that owns the Apps Script. You can also trigger it manually at any time via OTG Admin → Send Health Email Now in the spreadsheet.

AI Privacy Redaction

When enabled in Factory Step 1, the AI report processor automatically removes worker names and other identifying information from visit notes before sending them to the Gemini AI API. This is a data minimisation practice and is strongly recommended when using any external AI service to process staff records.

You can toggle this on or off per deployment via the AI Privacy Redaction checkbox in Factory Step 1 → Safety & Fleet Options.

Welfare Checks

Welfare checks are periodic "Are you OK?" prompts during a site visit. They are off by default and are switched on in the Settings tab with WELFARE_CHECKS (see Part 4). They are never used on trips, because a prompt while driving is a distraction hazard. Worker phones follow the Settings tab; the value in config.json is only a fallback for a phone that has never been able to read the Settings tab, and the Factory writes it as off.

What happens

  1. At the welfare time the worker's phone shows a full-screen "Are you OK?" prompt. If the phone is locked, the server also sends a push to the worker's own phone: "Welfare check - open the app and tap I'm OK" (this needs phone alerts, see below).
  2. The worker has WELFARE_GRACE_MINS (default 2 minutes) to tap I'm OK. Opening the app after a check fell due shows the prompt at once with the time left.
  3. If the time runs out, the visit is treated as overdue from that moment. A standard visit alerts the main contact at once ("WELFARE CHECK NOT ANSWERED"), then again every 15 minutes, with the escalation contact joining at the fourth alert. A Critical Timing visit alerts both contacts at once, then again 5 and 10 minutes later.
  4. If the worker answers late, or clears the alarm with their PIN, contacts who were alerted receive an All Clear saying the visit is still being monitored, and the next check is set.

Good to know

  • Keep the app open or set up phone alerts. A locked phone freezes the app's timers. Without phone alerts, a worker who locks their phone gets no prompt, and their contacts are alerted at every check. The worker app shows an amber warning on the start and visit screens when welfare checks are on and phone alerts are not set up.
  • The worker app has a Check in now button. An early check-in also brings the next check earlier.
  • A check that falls at or after the visit's due time is skipped. Extending a visit restarts a check that was already due, so an extend never causes a false alert.
  • Switching WELFARE_CHECKS to Off does not stop an escalation that has already started.
  • Visits columns AD and AE hold the welfare state (do not edit). The daily Health email has a "Welfare checks" row.
  • Deploy the backend (build __51_ or later) before the worker app (__24_).

Phone Alerts for Workers

A worker can subscribe their own phone to a private ntfy topic so the system can nudge them before their contacts are alerted. In the worker app go to Settings > Phone alerts > Set up phone alerts. The app shows a private topic starting otg-, the ntfy server, and:

  1. Android: tap the link to open ntfy with the topic added. iPhone: tap Copy, then in the ntfy app tap + and paste.
  2. Let ntfy override Do Not Disturb for urgent messages, and turn battery optimisation off for ntfy (Android).
  3. Lock the phone, then press Send test. The message must arrive on the lock screen. Send test is limited to one a minute and the reply is shown exactly as received.

The topic is stored in Staff column J. Clear the cell to reset it.

When a reminder is sent

Reminders are sent only when the phone has gone quiet, so a healthy app never gets one, workers do not feel watched, and there is no notification fatigue.

  • "Visit ends in 5 min" / "Trip ends in 5 min" - Critical Timing visits and trips only, and only if nothing has been heard from the phone for more than WORKER_WARN_QUIET_W1_MINS (default 3).
  • "Check in now - your contact will be alerted in 3 min" - standard visits and trips only, and only if nothing has been heard for more than WORKER_WARN_QUIET_W2_MINS (default 6).
  • Never while an alarm is active. Reminders show only the site or destination and the due time.
  • Limited to WORKER_WARNING_DAILY_CAP a day (default 100). Alarms to contacts are never limited.
  • Switch them all off with WORKER_WARNINGS.

Reminders are a courtesy. They never replace the alerts to contacts.

What the Phone Reports, and When

  • Standard site visit: nothing is reported before the due time except the start and end. From the due time, an overdue visit reports at once and then every 5 minutes (on every screen mode).
  • Trips: the position is reported every 2 minutes.
  • Critical Timing site visits: a "still here" signal with no position is sent every 2 minutes for the last 15 minutes before the due time only. This lets the system notice a silent phone in time.
  • A locked phone stops reporting. That silence is what triggers the reminder push.
  • The server keeps only the time it last heard from the phone on each visit (Visits column AF), not a log of every contact.

What Contacts Receive

Alarms reach nominated contacts by ntfy push, email and (if configured) SMS. The ntfy alert carries a Call worker button and tapping the alert dials the worker; a Map or Site map button opens the location. This needs the ntfy proxy to forward the Click and Actions headers if you use the proxy (see the warning in ntfy Push Notifications above).

  • All overdue alerts arrive as urgent, the highest ntfy priority. Each contact should allow the ntfy app to override Do Not Disturb for urgent messages and test it with the phone locked.
  • Alerts say how long overdue the worker is, counted from the due time, and show times as am/pm. The All Clear does not.
  • After a PIN clear the overdue count restarts from the new due time.

DURESS alerts

A DURESS alert has no tap-to-call (tapping the notification does not open the dialler); the Call worker button stays. The alert starts with: "If you call: the call may be overheard. Keep it calm and ordinary, and listen for any code phrase you have agreed with [first name]." The app has no code-phrase setting, so each worker and their contacts should agree a code phrase in advance.

Travel Distance and the Travel Report

Distance may be used for travel claims, so the Travel Report shows how each distance was worked out. The app tries these in order:

  1. A road route along the worker's GPS trail (breadcrumbs).
  2. Straight lines along the trail.
  3. A road route from the start to the end of the trip.
  4. A straight line from the start to the end.

A locked phone leaves few breadcrumbs, so a long trip with the phone locked usually uses the start-to-end road route. A road route needs an OpenRouteService key; without one the straight-line methods are used. The figure may be raised to a minimum worked out from the vehicle's speed. The worker can always change the distance on the closing form.

Run OTG Admin > 3. Run Travel Report for a month. After Total km a Distance method column says, in plain words, which method was used ("road route along the GPS trail", "straight line start to end", "not measured - entered by the worker", and so on). When the worker changed the app's figure by 0.05 km or more, it adds "edited by the worker (app calculated 12.4 km)".

At the start of a trip the app warms up the GPS. If no position is found within about 5 seconds the trip still starts, and the closing form asks the worker to enter the distance. Pinch-zoom is blocked while the screen is dimmed and restored when the worker wakes it.

Site Safety Information (Procedures History)

A worker can upload site-safety photos from a site's info panel. The upload replaces the site's "Emergency Procedures" (Sites column J) on every Sites row of that site. Before anything is replaced, the old links are written to a visible tab called Procedures History (Time UTC, Time local, Site, Company, Sites Row, Worker, Previous Links, New Links, Matched By). Photos in Drive are never deleted, so old links keep working.

The upload is refused, and nothing in Sites changes, if the site cannot be matched, the same site name exists under two companies and cannot be told apart, there is no photo, a photo fails to save, the history tab cannot be written, or column J is in use under another header. The form itself is always saved, and the worker still sees "sent". Refusals are written to the Audit as procedures:no-match, procedures:ambiguous, procedures:no-photos, procedures:photo-FAILED, procedures:archive-FAILED, procedures:no-site, procedures:no-sites-tab, procedures:no-column or procedures:error; a good upload is procedures:updated. The site is found from the site name sent by the worker's panel, then from the form's Site Name and Company fields, then from the Location Name. Two companies with a site of the same name (for example "Head Office") are kept apart on the phone and in the backend.

Two Organisations on One Web Host

Two organisations can be hosted from one web host if each has its own folder. Worker app builds from __24_ keep each organisation's data on the phone under a name made from the whole backend address, move existing data across once on the first start, and limit Reset app data to that organisation's app. A browser tab that holds a running visit shows an amber "This is a browser copy - close it and open the Safety App from your home screen" bar.

Update both organisations' packs. From Factory index__14_ the service worker names its caches by install folder and, when it updates, deletes only its own older caches. An organisation still using an older service worker can, when it updates, delete the other organisation's caches, so update both. Caches left by the old naming remain on a phone until the worker taps Force App Update (which still clears every cached file on the host, for both organisations; the phone then needs a signal at its next start). Only app files live in these caches, never records.

System Diagnostics

The Run System Diagnostics function is a comprehensive health check that tests every integration and configuration item in your deployment. Run it after initial setup to confirm everything is working, after any configuration change, or whenever you suspect a problem with alerts not reaching contacts.

How to run it

Open your Google Sheet and go to 🛡️ OTG Admin → Run System Diagnostics. The function runs immediately and does two things simultaneously: it logs results to the Apps Script execution log (visible in the Apps Script editor under View → Logs), and it emails a formatted HTML report to your configured health email address.

Safe to run at any time. The diagnostic does not send any real alerts to workers' emergency contacts, does not consume SMS credits, and does not affect any visit data. The ntfy test posts to a private diagnostics topic, not to your contacts' topics.
